# Finite mock lifecycle fixtures

The opt-in `nodecraft_providers::mock` API (also available through provider-testkit and the legacy testkit reexport) keeps `MockProvider::new` and `MockModel` unchanged. Use `MockProvider::scripted` for finite failures. Pass owned models and `MockOperation` records containing a model, an operation id, and exact sent keys in replacement order. A `MockScript` independently configures submit_failures, lost_replies, poll_failures and failed_generations using `MockFailures { count, kind }`. Zero is absent.

Submit failures happen before acceptance; lost replies happen after one acceptance/bill and are consumed by same-key retries. Poll errors pause progress on the same handle. A provider-reported failed generation remains failed; its next declared key can be accepted only after that failure was observed. A successful or cancelled operation cannot start replacement keys. Accepted keys replay the original request even when later payloads change. Terminal failure/cancellation bypasses remaining lost-reply slots; successful results retain those slots.

Use one model with distinct operations for independent logical jobs. Future Driver fixtures should compute exact sent keys through engine::jobs::sent_key; the provider mock neither parses those strings nor imports engine. Unlisted keys for scripted models, mismatched declared keys and premature replacement keys refuse without acceptance. Unscripted models preserve legacy behavior, including permanent failures.

Configuration is limited to64 models/operations/keys per operation (4096 total keys),64 ASCII bytes per id/key,1024 failures per stage; failed generations require a following key and hence max63. Positive polling/terminal stages require a queued model. Clone shares progress. Reconstruct the configuration for isolation; independent instances may issue identical handles, so keep handles with their original provider. Method invocation has effects even if its returned future is dropped before polling, matching legacy behavior. Configuration limits do not bound caller-preallocated input memory or the existing request log. Errors never include supplied keys or ids. Submit delivery evidence remains conservative, not proof based merely on scripted error kind.
