## 2026-10-22 · Soul IDs are listed from the account and checked before a run is paid (#180)

- **`higgsfield.soul_ids` is an option source.** It lists the account's Soul IDs from
  `GET /v1/custom-references/list`, valued by id and labelled by name, fixed in
  `crates/engine/src/option_fetch.rs` like the restyle presets. Each Higgsfield list is asked for
  on its own, so a failing list never keeps the other from loading.
- **Only usable identities are listed.** SOUL 2 takes Soul IDs trained with `model_version: "v2"`;
  ones still training, failed, or trained for another SOUL are left out of the picker. Pending and
  failed identities come back when training lands in NodeCraft (#680).
- **The list is parsed strictly.** Higgsfield documents the reference object but not the list's
  reply, so a page must be a list of references, bare or under `items`. Anything else is refused
  rather than guessed at, and an account with more than 20 pages of 50 is refused rather than
  listed in part.
- **Readiness is checked when the body is staged, before anything is paid.** A Soul ID belongs to
  one account and can be mid-training, so a cached list can't vouch for it. The adapter reads the
  documented `GET /v1/custom-references/{id}` once per staged body and refuses an id the account
  doesn't have, one not completed, or one for another SOUL. A retry of the same job replays the
  checked body without asking again, keeping retries free of extra calls.
- **Creating a Soul ID is not replayed blindly.** Training costs money and Higgsfield documents no
  idempotency key for `POST /v1/custom-references`; when creation lands, an ambiguous POST failure
  must be resolved by listing, never by sending it again.
