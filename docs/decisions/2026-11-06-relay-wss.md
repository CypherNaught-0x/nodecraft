## 2026-11-06 · The relay serves wss:// itself, beside ws:// (#1067)

A browser on an HTTPS page may only open `wss://`, so a remote relay needed a TLS proxy in front
of it. Now `nodecraft-cli relay --tls-cert <pem> --tls-key <pem>` serves TLS itself.

- **Both, on two ports.** The desktop client connects with plain `ws://` (it has no TLS
  WebSocket client), so a relay with a certificate keeps serving `ws://` on `--listen` and adds
  `wss://` on `--tls-listen` (the next port by default). Both listeners reach the same rooms and
  share the connection limits, so a desktop peer and a browser peer can share one room.
- **The platform's TLS stack.** rustls with aws-lc on Linux and other Unix, the operating
  system's (native-tls) on Windows and macOS: the same split the providers' HTTPS uses, so no new
  TLS library and no C toolchain where the workspace avoids one. Certificate and key are PEM; on
  Windows and macOS the key must be PKCS #8.
- **Bounded like the hello.** Each handshake runs on its connection's own thread with the
  hello's 10 s timeout on every read and write (an idle limit, as for the plain WebSocket
  handshake, not a total one), and counts against the per-address waiting limit shared by both
  listeners, so stalled handshakes hold only their own slots.
- **Links name one address.** A desktop owner's share link carries the `ws://` address; a browser
  on an HTTPS page uses the same link with `wss://` and the secure port. Sharing links that name
  both is left for later. Files are read once at start, at most 1 MiB each; errors name the file,
  never its contents.
- **Not here:** reloading a renewed certificate without a restart, and a TLS client in the
  desktop app.
