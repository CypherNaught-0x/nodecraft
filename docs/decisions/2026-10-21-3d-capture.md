## 2026-10-21 · 3D captures: photo and view sheet as action nodes, seeded from the viewer (#112)

- **A capture is an action node, wired to its model.** "3D photo" (`mesh.photo`) and "3D view
  sheet" (`mesh.views`) take one 3D model and give one image. They draw the model offscreen with
  the viewer's own renderer (`nodecraft-gpu`) and stage an ordinary PNG, so the result is an
  ordinary image asset any image input takes. Because the capture is a node downstream of the
  model, a changed model marks it stale like any other node; its provenance is its edge.
- **The camera is the node's parameters; the viewer only seeds them.** The viewer's orbit stays
  view state (#111). The card's Photo and Views buttons dispatch `mesh.capture`, which adds the
  capture node with the viewer's yaw, elevation, zoom and style as its parameters and wires it to
  the model, as one changeset (one undo step). Re-running the node draws the same image whatever
  the viewer did since; changing the angle is an ordinary, undoable parameter edit. Angles are
  saved in whole degrees and zoom in steps of 0.05, so a capture repeats exactly.
- **A view sheet is one image, row-major.** 4, 8 or 16 views (2×2, 4×2, 4×4) at equal steps
  round the model, starting at the start angle and turning counter-clockwise (seen from above) or
  clockwise, read left to right, then top to bottom. One contact sheet, not one image per view:
  a list output would need a split to be useful, and a split node already turns a grid into
  tiles. These counts are the capture's own; they are not a 3D provider's input-view limit.
  Tiles carry no drawn labels: a tile's angle follows from the node's start, count and
  direction, which are saved with it. Per-tile labels and angle metadata are a later addition.
- **Background and alpha are parameters.** The default background is transparent. Background
  and line colours are premultiplied before drawing and the read-back image is turned straight,
  so model edges over any background, translucent or not, keep their colours.
- **Bounded.** A photo is at most 2048 × 2048 pixels and a sheet view at most 1024 × 1024, so a
  16-view sheet is at most 4096 × 4096, within the default image limit. A whole capture must
  draw and read back within 40 seconds, shared between its views; a view that overruns its share
  marks the GPU unusable and the next capture starts on a fresh device (the hung one is leaked
  rather than dropped, since dropping it may wait on its work). No GPU is an error the card shows,
  never a panic. A device smaller than a requested size draws the largest image it can.
  Local actions have no cancellation hook yet, so a capture in progress finishes or times out.
- **Not in the browser yet.** WebGPU only hands out a device asynchronously and local actions run
  synchronously, so in the browser a capture reports that no GPU is available.
- **One capturer per process.** Captures share one headless device behind a mutex natively (a
  thread-local in the browser); they run one at a time, which is what one GPU does anyway.
- **The turntable video is follow-up work.** It needs a frame encoder for the video path, which
  is not on `main` yet; it will be its own node reusing this renderer.
