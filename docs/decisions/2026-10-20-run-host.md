## 2026-10-20 · Runs are driven by an engine-side host the shell pumps each frame (#409)

- **The host lives in the engine.** `run_host::RunHost` holds what the driver goldens proved:
  authorize the prepared run, queue its jobs (model jobs with their media, sources and local
  actions on the source runner), drive them on an injected `Runtime`, absorb what the driver
  reports, settle reservations, and record results. The shell only supplies a runtime and a
  `JobBudget`, calls `pump` once a frame, and shows the notices. The CLI and MCP server can
  reuse it as is.
- **Callbacks only post messages.** The driver's events, the runner's deliveries and the `add`
  verdicts go into a per-run mailbox. The session is touched only in `pump`, on the thread that
  owns it, so nothing needs to lock the document.
- **One step per `run.record`.** Each finished step is recorded as soon as it finishes, in its own
  call. A large result can't push the others past the 1 MiB parameter limit, and an earlier step's
  result isn't held back by a slow sibling. A refused record is reported as that step's failure.
- **Every ended model job is let go.** Done, failed, cancelled, skipped, refused by the scheduler,
  or a result that can't be converted: each calls `ProviderRunner::forget`, which settles the
  reservation first. The ledger never keeps a reservation for a job that is over.
- **Budget resources follow the ledger.** After any model job ends, the host swaps in a fresh
  `BudgetState` and `UsageSnapshot` from the shared usage log, so the next quote counts what was
  just spent. `install` puts them in place before the first quote.
- **Bounded.** Up to `MAX_RUNS` runs wait in the inbox, and up to `MAX_RUNS` are in flight;
  `run.start` beyond either is refused with `Busy`. A mailbox holds at most one message per job
  state change, which admission already bounds.
- **A job that can't be prepared fails alone.** If a model job's media is missing or too large
  when it's queued, that job fails before anything is sent, and the rest of the run carries on as
  far as it can.
- **Not yet:**
  - the usage log and the submitted handles aren't saved, so quitting mid-run doesn't resume and
    its open reservations go with the process;
  - media is read on the UI thread when the job is queued;
  - the desktop app doesn't build a host yet (a tokio runtime, Reqwest and keychain keys).
